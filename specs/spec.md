# 豬豬顧問 — 功能規格

版本 0.2(草稿,待確認) · 2026-08-08

> 本文只描述**做什麼**與**為什麼**,不描述**怎麼做**。
> 技術選型、架構、檔案結構一律留到 `plan.md`。
> 受 `constitution.md` 約束。

---

## 1. 這是什麼

給台灣豬場經營者與現場獸醫使用的顧問工具,做兩件事:

1. **疾病與用藥諮詢** — 描述症狀,取得可能病因、用藥方向與風險評估
2. **生產指標健檢** — 輸入自家牧場數字,對照全國 110 場常模,取得評級與改善優先順序

兩者共用同一個顧問人格,但走不同的處理路徑(見第 5 節)。

## 2. 為什麼要做

現場的痛點:

- 豬隻出狀況時,獸醫不一定馬上到得了,飼養人員需要當下的初步判斷方向。
- 生產指標年報每年發一次,是一張靜態的表。牧場主要自己拿尺去比對自己落在哪一段,再自己想該從哪裡改起 —— 多數人不會做,做了也不知道下一步。
- 既有系統(豬場e把抓)強在資料登錄與帳務,弱在「所以我該怎麼辦」。

本工具補的是**判讀與建議**這一段。

## 3. 使用者

| 角色 | 情境 | 最在意 |
|---|---|---|
| 牧場飼養人員 | 現場發現異常,手機或電腦查詢 | 快、看得懂、知道下一步 |
| 牧場經營者 | 年報出來後想知道自己排哪裡、該投資什麼 | 準確、有依據、能排優先順序 |
| 現場獸醫 | 快速查核用藥劑量與休藥期 | 資訊完整、標明不確定性 |

## 4. 範圍

### 做

- 疾病症狀諮詢與用藥建議(含風險評估)
- 生產指標輸入、評級、常模比對、弱項排序、改善建議
- 兩項功能的結果呈現與匯出

### 不做

- 牧場帳務、庫存、進退貨
- 豬隻個體資料登錄與族譜管理
- IoT 感測器串接與環控
- 多牧場帳號與權限管理
- 影像辨識診斷

不做的理由見 `constitution.md` 第八條。

## 5. 使用者故事

### US-1 疾病用藥諮詢

**身為**飼養人員,**我想要**用自己的話描述豬隻症狀,**以便**得到可能病因與處置方向。

驗收條件:

1. 假設我輸入「保育豬咳嗽喘氣」,當我送出,則回應必須包含:可能病因(分類列出)、建議藥品與用法、風險評估(副作用/休藥期/抗藥性)、獸醫確診提醒。
2. 假設我輸入的問題與豬隻健康無關,當我送出,則系統應婉拒並說明服務範圍,不得硬答。
3. 假設回應正在生成,當內容尚未完成,則畫面必須即時顯示已生成的部分,不得只顯示等待動畫。
4. 假設我的輸入命中 `reference/reportable-diseases.md` 的關鍵字組合,當系統回應,則必須附加固定樣板的通報提示區塊,且此判斷不經過 AI(憲法第一、二條)。
5. 假設輸入為空白或超長,當我送出,則系統應明確告知原因,不得靜默失敗。
6. 支援追問:顧問可參考同一次瀏覽期間的前 20 則對話。
   **對話歷史只存在使用者的瀏覽器,伺服器不保存任何人的問題內容** ——
   若由伺服器依 IP 保存,共用對外 IP 的同事之間會看到彼此的對話,屬隱私外洩。
   歷史由前端隨請求帶上,因此伺服器必須自行裁切則數與單則長度,不信任前端資料。
   每則回答仍須能獨立看懂,不得出現「詳見上一則」這類需要回溯才完整的內容 ——
   使用者可能只看最後一則就去用藥。
7. 假設使用者已完成過生產指標健檢(US-3),當我進行疾病諮詢,則系統應把本場已知弱項(如離乳前死亡率評級)當作背景資訊提供給 AI 參考,回應可視情況呼應該弱項。此為單向資料流:健檢結果 → 諮詢背景,不反向。
8. 假設使用者從未做過健檢,當我進行疾病諮詢,則系統正常運作,不要求必須先完成健檢。

### US-2 生產指標輸入

**身為**牧場經營者,**我想要**輸入自家年度生產數字,**以便**系統為我評級。

驗收條件:

1. 假設我只知道部分指標,當我只填其中幾項,則系統仍應對已填項目評級,並標示哪些因缺漏而未評。
2. 假設我輸入的數值明顯不合理(如分娩率 300%、懷孕天數 5 天),當我送出,則系統應在計算前擋下並指出問題欄位。
3. 假設我填入的指標之間可互相推導(如年產胎數 vs 非生產天數+哺乳天數),當數值彼此矛盾,則系統應提示不一致,但不阻止繼續。
4. 我應該能看到每個欄位的定義說明,不需另外查手冊。

### US-3 常模比對與評級

**身為**牧場經營者,**我想要**知道每項指標在全國 110 場中的位置,**以便**判斷哪裡落後。

驗收條件:

1. 假設我輸入一項指標值,當系統評級,則必須輸出 A~F 級距,且結果與官方年報演算法一致。
2. 假設同一組輸入送出兩次,當系統評級,則兩次結果必須完全相同。
3. 假設某指標屬「規模型數值」(如總配種數),當系統處理,則不得評級,僅顯示對照。
4. 每個顯示的常模數字都必須標註來源與年份,樣本數不足 110 者必須顯示實際樣本數。
5. 評級結果必須同時呈現本場值、全國平均、以及本場落在哪個百分位區間。

### US-4 弱項診斷與改善建議

**身為**牧場經營者,**我想要**知道該優先改善哪一項,**以便**把資源花在刀口上。

驗收條件:

1. 假設我完成評級,當系統產出報告,則必須依「落後程度 × 對 PSY 的影響」排出改善優先順序,而非只按級距排序。
2. 假設某指標評為 E 或 F 級,當系統給建議,則建議必須具體可執行(例:「檢視哺乳期採食量」),不得只說「建議改善」。
3. 假設兩項指標有因果關係(如離乳前死亡率 → 母豬平均離乳仔豬數),當系統給建議,則應指出上游指標,避免使用者頭痛醫頭。
4. 改善建議由 AI 生成,評級與排序由程式計算,兩者在畫面上必須可區分(憲法第二、三條)。

### US-5 結果留存

**身為**使用者,**我想要**把諮詢結果或健檢報告帶走,**以便**跟獸醫或員工討論。

驗收條件:

1. 我應該能將結果匯出成可離線閱讀的檔案。
2. 匯出內容必須包含免責聲明與資料來源年份。

## 6. 兩條路徑的差異

這是本規格最重要的設計決定:

| | US-1 疾病諮詢 | US-3 生產指標評級 |
|---|---|---|
| 誰負責產出結果 | AI 生成 | 程式計算 |
| 同樣輸入是否給同樣輸出 | 否(可接受) | **是(必須)** |
| AI 的角色 | 主體 | 只負責解讀與建議 |
| 出錯的後果 | 使用者看得出不對勁 | 使用者看不出來,會直接照做 |

因此生產指標的評級**絕不可**經過 AI。AI 拿到的是「已經算好的級距」,它的工作是解釋和建議。

### 整合點(單向)

兩條路徑不是完全隔離。US-3 健檢結果算出的「本場弱項」,可以當作背景資訊注入 US-1 疾病諮詢的 AI 上下文,讓回應更貼近本場實際狀況(見 US-1 驗收條件 7、8)。

資料只單向流動:**健檢結果 → 諮詢背景**。疾病諮詢的 AI 回應不會、也不應該反過來影響健檢評級——評級永遠只認計算結果(憲法第二條第五款)。

沒做過健檢的使用者,疾病諮詢功能必須照常運作,不得要求先完成健檢才能用。

## 6.5 介面與展示決定

| 項目 | 決定 |
|---|---|
| 版面 | 上方兩個頁籤切換:「疾病諮詢」與「生產健檢」 |
| 主要使用者 | 牧場經營者與潛在客戶 —— 用語要一眼看懂,避免技術術語 |
| 範例資料 | 範例牧場 2025 年實際數據(已取得授權),提供「載入範例」按鈕 |

### AI 不可用時的降級行為

訂閱額度為滾動視窗,可能在使用中耗盡。此時:

1. **生產健檢(US-2、US-3、US-4 的評級與排序部分)必須完全正常運作** ——
   這些是純計算,本來就不需要 AI 或網路。
2. 疾病諮詢(US-1)停止服務,並明確顯示原因(額度限制),不得顯示通用錯誤訊息。
3. 生產健檢的「改善建議」由 AI 生成,此部分停止,但評級、百分位、弱項排序照常顯示。

驗收條件:切斷 AI 層後,生產健檢的完整流程仍能跑完並顯示結果。

## 7. 非功能需求

| 項目 | 要求 | 理由 |
|---|---|---|
| 首字回應時間 | AI 諮詢 3 秒內出現第一段文字 | 現場不會盯著空白畫面等 |
| 評級計算時間 | 即時(無感) | 純計算,不該有等待 |
| 語言 | 繁體中文,台灣豬業術語 | 使用者是台灣現場人員 |
| 主題 | 淺色與深色皆可讀 | 豬舍現場光線差異大 |
| 認證 | claude.ai 訂閱額度,無 API key | 憲法第五條 |
| 安全 | 網頁輸入送進 AI 時零工具權限 | 憲法第四條 |
| 離線能力 | 評級功能不依賴網路 | 純查表計算,沒理由要連線 |
| 用量保護 | 單題字數上限 2000;每 IP 每小時 20 次;連續請求間有最短間隔;額度異常時明確告知 | 憲法第九條。對外上線走 API 計費,失控會直接扣款 |
| 使用者識別 | 取代理標頭中**倒數第 N 個** IP,不可取第一個 | 前段可由使用者偽造,取第一個等於讓攻擊者自行指定身分、無限重置額度 |
| 防護狀態上限 | 限流紀錄須自動清除過期來源 | 無上限成長的紀錄本身就是攻擊面 |

## 8. 成功條件

本專案在下列條件全部成立時視為達成:

1. 用範例牧場 2025 年報的實際數據輸入,系統產出的 18 項評級與官方報告完全一致。
2. 疾病諮詢能回答訓練資料以外的開放式問題,而非固定關鍵字比對。
3. 全部純計算邏輯有自動化測試,且不需要網路或 AI 即可執行。
4. 未登入 CLI 時,系統明確告知登入方式,不會退回假資料或靜默失敗。
5. `reference/reportable-diseases.md` 清單中的每個關鍵字組合都有對應測試案例,確認命中必觸發、不命中不誤觸發。
6. 連續快速送出多個問題時,用量保護機制會生效並提示使用者,而非讓請求無限制打向 CLI。

## 8.5 展示風險

demo 對象是牧場經營者與潛在客戶。客戶會把畫面上的內容當成產品承諾,
因此下列兩項在對外展示時必須明確標示,或考慮暫時隱藏:

| 風險 | 現況 | 對外展示時的處理 |
|---|---|---|
| 弱項排序權重未經專家覆核 | `provisional=True` | 畫面必須標示「暫定排序」;若客戶會據此做投資決策,建議先取得專家覆核 |
| 法定傳染病清單不完整 | 僅涵蓋三大豬病 | 必須標示「非完整清單,不可作為合規依據」;漏報的責任風險高於不做 |

第二項尤其需要判斷:一個**看起來**會提醒法定傳染病、實際上只認得三種病的功能,
可能比完全沒有這個功能更危險 —— 使用者會以為沒跳提示就是安全的。

## 9. 待確認事項

以下需要專案持有者裁決,會影響 `plan.md`:

1. **輸入方式** — 生產指標是逐欄手動輸入,還是支援上傳年報 PDF 自動解析?後者體驗好但實作成本高數倍。
2. **常模資料更新** — 2026 年報出來後,是改資料檔就好,還是需要介面讓使用者自行上傳新年報?
3. **歷史紀錄** — 是否需要保存歷次健檢結果以看趨勢?這會引入資料儲存,範圍擴大。
4. **多場比較** — 使用者若管理多個牧場,是否需要並列比較?
